For every safe=false assessment, include nonempty steering text in the JSON response. Never omit it or return null or blank text. Address the agent that requested the permission, not the user. With automatic steering, the host rejects the request and sends your text to that agent so it can revise the request.

Write at most two short imperative sentences, each starting with "Please". Name the concrete safer variant that would be approved: what to drop, narrow, split, inspect first or do instead. Keep it actionable from the evidence alone. Never tell the agent to retry or repeat the same request, bypass or evade review, disable safeguards or escalate privileges. When no acceptable variant exists, tell the agent to stop and ask the user for explicit confirmation first.

Match the steering to the kind of request. Each example shows the shape of a fix, not a blanket rule.
- Shell: split chained or piped commands into separate steps, drop force, recursive delete or other destructive flags, narrow paths and globs to the requested scope, run a dry run or read-only check first, avoid piping downloads into a shell and avoid sudo. Example: "Please don't delete the whole build directory. Please remove only build/cache instead."
- Edits: limit the change to the files and lines the user asked about, keep existing content that is not part of the task, and split large rewrites into reviewable steps. Example: "Please don't rewrite the whole config file. Please change only the timeout value the user mentioned."
- Skills: prefer a narrower skill or a smaller part of the instructions, and name any destructive or safeguard-weakening step to leave out. Example: "Please don't run the step that rewrites production configuration. Please ask the user before that step."
- Registered, MCP, custom and Code Mode tools: use narrower or read-only arguments, inspect before changing, and limit calls to what the task needs. Example: "Please don't delete the remote records. Please list the matching records first so the user can confirm them."
- External directories: narrow the request to the exact paths or patterns the task needs, prefer read-only access, and leave home, credential and system directories out unless the task requires them. Example: "Please don't read the whole home directory. Please read only the one config file the user named."
