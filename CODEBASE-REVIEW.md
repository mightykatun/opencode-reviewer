# OpenCode Reviewer code review

Reviewed `277e64d` (reviewer 2.8.7) against stable OpenCode **2.3.2** on November 18, 2026. Line references are to that commit. Savings below are estimates of physical lines, including comments and blanks, unless marked as measured. They are net estimates for a proposed change, not a diff or a promise.

**Verdict:** Fix the confirmed Code Mode regression before calling this release compatible with the latest host. Updating the SDK alone does not fix it. Keep the evidence and single-write machinery. The worthwhile deletions are at the edges: how the terminal is packaged, how history gets keyboard focus, and how Linux notifications are delivered. The highest-priority trust issue is that terminal-local credentials and automation accept options supplied by the connected server.

## 1. High-impact OpenCode modernizations and code savings

**Fix Code Mode's identity model before optimizing it.** Since [2.3.1](https://github.com/anomalyco/opencode/releases/tag/v2.3.1), each inner tool execution has its own ID in plugin hooks. The native permission still points at the outer `execute` row ([upstream change](https://github.com/anomalyco/opencode/pull/64324)). `src/invocation-capture.ts:50-61,73-78` only adds a candidate when the inner event has the **same ID** as the outer capture. With distinct IDs, the capture goes into a separate entry and its data never reaches the outer candidate list at lines 106-110. On 2.3.2 the real fixture reached the verdict request and failed `scripts/smoke-v2-review.mjs:1408-1413`: “Completed siblings remain explicitly uncertain observations.”

The exact outer program is still reviewed, and the failed fixture does not establish that a wrong permission was granted. But the judge is allowed to return Safe despite uncertain linkage, so missing the resolved inner arguments and definitions is consequential. Keep the durable outer identity as mandatory evidence. Track a bounded set of same-session, same-message hook observations during the outer call as explicitly **possible** candidates, including completed calls. Multiple outer calls can overlap. Never present message equality, timing or arrival order as a proven parent link. Prefer a public outer-ID field if upstream exposes one. Preserve shared-ID behavior for older hosts without gating by version. Update `src/host-code-mode.ts:22-24` and exercise distinct IDs, overlapping outers and the existing real fixture. This change earns its place on correctness, even if it adds lines.

**Native substitutions I would decline:**

* The [server permission `evaluate` hook](https://opencode.ai/docs/build/plugins/server#permissions) is the most tempting rewrite. It runs **before** publication of a native request, for both `allow` and `ask`. Deciding there removes the pending request that the countdown, Cancel, route ownership, manual decision hold and confirmed history depend on (`src/controller.ts:554-615`, `src/host-permissions.ts:73-107`). It is a reasonable basis for a different server-only policy engine. It cannot preserve the current product's user veto.
* `src/host-queue.ts:18-81`, `src/session-ancestry.ts:68-92`, `src/host-invocation.ts:17-37`: cached root and family IDs are useful for presentation. They do not prove complete ancestry, the current front permission, exact tool input, or companion epoch. Keep the authoritative checks before a reply.
* `src/reviewer.ts:218-245,274-310`, `src/retrieval.ts:125-152`: `experimental.generate.text`, `experimental.generate.decisions` and `session.generate` are different contracts from arbitrary Chat Completions endpoints with tool turns, independent keys, streamed previews, retries and per-POST accounting. The repo already uses `session.generate` where its session context is wanted, in `src/clarification.ts`. Moving the verdict to host-configured models could be a separate product mode. It is not a transport cleanup.
* `src/session-mode.ts:37-55`, `src/session-instructions.ts:81-108`: native synchronized JSON storage is attractive, but the enabled bit authorizes automation. The [tagged 2.3.2 storage implementation](https://github.com/anomalyco/opencode/blob/v2.3.2/packages/tui/src/context/storage.tsx) returns `initial` for **both** a missing file and a read or parse failure. No choice of `initial` preserves both “missing means enabled” and “unreadable means suspended.” It would also need migration of existing disabled records. Native **session instruction entries** are the wrong audience for private reviewer-only text. They change what the main agent sees.
* `src/history-schema.ts:486-514`: absence of a current session-deletion producer does not make the old deletion and privacy tables dead. Other versions can share this database. Keep read-side tombstones and recovery of work left by older writers.

## 2. Critical issues and dangerous failure modes

These are ranked by impact and prerequisites. None is a demonstrated unauthenticated compromise.

**Steering rejection has a wider effect than the reviewed permission.** The [2.3.2 permission implementation](https://github.com/anomalyco/opencode/blob/v2.3.2/packages/core/src/permission.ts#L327-L355) rejects **every pending sibling with the same session and source message** when one request is rejected. Version 2.3.1 narrowed this from a wider session-level cascade. `src/host-permissions.ts:92-107` makes one native write, but “one write” does not imply “one affected request.” Siblings can receive the same steering without independent Unsafe verdicts. History records their native rejects (`src/history-coordinator.ts:116-131`), while only the targeted dispatch gets an automatic-rejection record (`src/history-coordinator.ts:140-149`). A sibling with a saved outcome can consequently show up in the manual-rejection count.

**Fix:** Document the batch effect. If per-request steering is a product guarantee, keep ambiguous concurrent asks manual until the host offers an isolated reject, since a list check cannot exclude a sibling arriving immediately after it. Keep direct reviewer dispatches distinct from unattributed native rejections. Add a two-permission, single-message fixture covering both the agent feedback and both outcome counts. This finding comes from the tagged host implementation, not from a steering fixture run.

**High: Inherited server configuration selects a secret from the terminal's environment and its destination.** `src/companion.ts:29,127-132` returns the entire options object. If local TUI options are empty, `src/cli-plugin.ts:32-37,80-91` accepts those options. `src/chat-transport.ts:6-9` resolves the named environment variable locally. `src/reviewer.ts:214,282-285` sends its value to the configured URL. The same design applies to retrieval credentials. This is consequential with a less-trusted remote server or less-trusted effective location configuration: the server chooses both sides of a transfer of a **client-side** secret. Conversely, an inline server key is included in the configuration response to an authorized RPC caller. A location and epoch check establishes which companion replied, not who authorized that credential use. This need not cross a new trust boundary on a single-user, fully trusted local host.

**Fix:** Keep credential references and their allowed endpoint pairing under local terminal control, or keep provider transport and credentials together on the trusted server. Return only nonsecret settings over the configuration RPC. Keep opt-in to automatic decisions local when connecting to other trust domains. `README.md:35-42,104-106` should show an environment-only example. Cover both directions with sentinel credentials and mocked transports. `src/config.ts:100-109` also allows bearer credentials over cleartext HTTP to a non-loopback host. Keep local HTTP model servers working, but require an explicit trusted transport choice for remote credentials.

**High: A stuck settings read leaves automation enabled past the mode-refresh deadline.** `src/session-mode.ts:117-139` catches the five-second deadline, then awaits the underlying read **before** setting the cached value to false. If that read never settles, `refreshing` remains occupied, the old `true` is still visible to `src/controller.ts:429`, and `src/host-runtime.tsx:449-457` never receives the changed roots. One root also blocks later roots in the serial sweep. This matters when a user disables review from a second terminal or when the shared state filesystem stops responding.

**Fix:** At the logical deadline, revoke eligibility and notify the controller for the affected root immediately. Retain the read's physical capacity slot until it settles. Check the root's revision before publishing, bound the age of a positive mode for other blocked roots, and refresh only roots with active consumers. `test/session-mode.test.ts:72-99` covers corrupted records and a late successful read. Add a deferred read that stays outstanding past the deadline and assert the gate is disabled before releasing it.

**High confidentiality impact with an external provider: retrieval can disclose a secret before the underlying operation is approved.** `prompts/RETRIEVAL-PROMPT.md:2-8` explicitly suggests inspecting `.env`. `src/retrieval-tools.ts:63-69` accepts absolute and home paths. An inspection result goes into the retriever conversation at `src/retrieval.ts:213-215,349-355`, and a selected attachment goes into the verdict at `src/reviewer.ts:239-246`. Neither an Unsafe verdict nor a later Cancel takes back those bytes. `src/history-coordinator.ts:85-93,140-149` also preserves model-authored text, so a quoted value can outlive the review. This is a data-handling risk with the documented defaults, not a claim that a provider stores or misuses requests.

**Fix:** Make the default retrieval policy avoid secret-bearing contents and let the user explicitly authorize sensitive or out-of-project reads. Enforce restrictions at the companion's canonical file boundary, including direct attachments and search, before either model can receive the result. Supply variable names or a factual omission when values are unnecessary. Add a no-secret-quoting rule for report and steering text as a secondary measure. Document the two provider destinations and distinguish “read-only” from “stays local.”

**Operational risk: the retriever has per-result bounds but no practical cumulative conversation bound.** `src/retrieval.ts:131-152,213-215,349-355` keeps prior successful results and serialized tool messages, then serializes the entire conversation again on each turn. `src/config.ts:149-161` allows 50 rounds, 10 inspection calls per round and 16 MiB per result. The theoretical content alone is **7.8 GiB** at those settings, before copies. Actual provider, deadline or JS string limits will usually fail first. Even the defaults can accumulate about **3.75 MiB** of inspection results and repeatedly send the prefix. `maxFiles` constrains final forwarding, not this memory or network cost.

**Fix:** Budget bytes for the whole retrieval conversation separately from forwarded evidence. Stop additional inspections before serialization exceeds capacity, keep a bounded selection store, and finish with an explicit limitation. Test several individually valid results that together exceed the stage budget. This is a bound derived from code, not a measured production outage.

**Compatibility risk: the human decision guard depends on undocumented renderable IDs.** `src/host-approval-ready.ts:17-39` recognizes particular action groups and theme colors. An ambiguous *recognized* group holds automation. If upstream renames the whole group, the traversal finds nothing and returns false, exactly as it does when there is genuinely no presented prompt. `test/host-approval-ready.test.ts:12-35` explicitly locks in the latter behavior. The upstream TUI guide says host renderable structure is not a plugin API. The real `normal-decision` fixture passed on 2.3.2, so this is a future compatibility hazard, not a known wrong reply on that release.

**Fix:** Seek a public permission interaction-state accessor. Until then, run the native `normal-decision` and `fast-decision` scenarios on upstream V2 changes. Distinguish unknown visible interaction state from a positively absent prompt where the host permits it. Retain the independent open-tab path and the rule that sidebar paint never authorizes a write.

**Release integrity: a rerun can replace the GitHub archive before discovering an npm conflict.** `scripts/github-release.mjs:38-47` passes `--clobber` for an existing release. `.github/workflows/release.yml:166-178` does this after validating the new archive but before checking the published npm version. A validated rebuild can still differ from an existing asset. On a mutable GitHub release this can leave the two distribution channels serving different bytes even though the job ultimately fails. On a repository enforcing immutable releases the upload can fail even when the bytes already match.

**Fix:** If the asset exists, compare its digest to the validated tarball. Skip upload on equality and stop before mutation on mismatch. If absent, upload once without clobber. Keep GitHub-before-npm ordering for new releases. Replace the assertions that currently *require* `--clobber` at `test/release-version.test.mjs:99` and `test/release-workflow.test.mjs:231` with equal, different and missing-asset cases.

## 4. Cleanup and quick wins

* **Remove duplicate audio bytes, keep both notification kinds.** `scripts/build.mjs:15-19`, `scripts/bundled-sounds.mjs:15-28`, `src/notification-audio.ts:52-62`: `sounds/unsafe.mp3` and `sounds/attention.mp3` have the same SHA-256 and are each 75,122 bytes. One shared payload with two logical mappings removes **100,164 base64 characters** from the uncompressed bundle and optionally one 75,122-byte source asset. Preserve `unsafe.wav` and `unsafe.mp3` overrides. Adapt the package-byte check to prove both names resolve to the correct original bytes.
* **Remove unused transport variants rather than private type exports wholesale.** `src/host-permissions.ts:27-31,125-129,139-152`: production uses `pendingScope()` and the guarded `get()` inside `reply()`. `listScope()` and the per-session `list()` are exercised in tests but are not called by production. Redirect tests to the real inventory path, including the identity-only manual blocker. About **20 runtime lines**. `src/file-access.ts:13-14,110-113` also has an unused `FileScope.capture()` and `captureMs`. The live cwd canonicalization and its physical I/O ownership should stay. TypeScript with both unused checks enabled reported no unused locals or parameters. That does not identify test-only exports, generated worker inputs or fixture seams.
* **Parse notification settings once.** `src/cli-configuration.ts:21-25`, `src/config.ts:79-82,133-135`. The CLI parses desktop settings, `parseConfig` parses them again, and a failure is handled by manufacturing a replacement options object. Split the two parsers, then compose their results. Keep notification-only fallback and isolate desktop configuration errors from review.
* **Stop normalizing one URL per stream frame.** `src/usage.ts:24-32,68-80`: `usageAttempt` already computes the endpoint's accounting mode, then `responseUsage()` computes it again for every observed envelope, including deltas with no usage. Pass the mode into a private parser. Keep the exported boundary tolerant of unnormalized input.
* **Use the standard deferred-promise primitive in tests.** Local `deferred` helpers recur across roughly 30 test files. Compare `test/session-mode.test.ts:91-98` with `test/runtime-runner.test.mjs:22`. Node 26 has `Promise.withResolvers()`. Set the TypeScript `lib` appropriately (`tsconfig.json:3`) and keep custom deferreds only where they instrument settlement. Estimated **80 to 120 test lines**, independent of the fixture savings above.
* **Make the setup example copyable.** `README.md:35-42,83-106`: the literal key overrides the environment setting, and the example prompt directory is a required edit before review can start. Lead with a working minimal environment-only example and leave the full option inventory below. Fix “Rwo-entry” at line 90. Explain that provider requests include inspected evidence before the native permission is resolved.

### What I would protect during any reduction

`src/approval-transaction.ts` and `src/host-permissions.ts:73-123` separate reservation, single dispatch, HTTP acknowledgement and matching native resolution. That is the right model for a non-retryable permission write. `src/review-admission.ts:9-24` and `src/transport-ownership.ts:3-18` also make a distinction many systems miss: a deadline can end the user's wait without proving that physical work has stopped. The mode-refresh bug is a reason to apply that pattern more consistently, not to delete it.

`src/host-invocation.ts:17-37` binds evidence to the running call instead of inferring an operation from the permission label. `src/config.ts:57-65` prevents credential inheritance across different retrieval endpoints once the local configuration is trusted. `src/diagnostics.ts:13-22` constructs a fixed observation payload rather than letting arbitrary request data reach diagnostic sinks. All three are good examples of narrow interfaces doing useful work.

The release architecture is also worth preserving. `.github/workflows/release.yml:159-173` passes the validated archive by artifact ID and checks its actual bytes in the publish job. Fixing the existing-asset branch strengthens that design without moving build execution into a privileged job.
